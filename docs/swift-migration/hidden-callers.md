# Callers the compiler cannot see: selectors, the runtime, macros, and xib files

Part of the Objective-C to Swift migration process. Read
[README.md](README.md) first.

A method in this codebase can be called without its name appearing next to a
call. A port that renames it, changes its signature, forgets `@objc`, or drops
it as unused then breaks a caller that no compiler and no simple search will
report. Many of these failures are silent: a menu item that is permanently
disabled, a delegate method that is never called, a setting that no longer
loads.

## 1. Two defenses

**Preserve the runtime surface.** In stage one every class keeps its name and
every method keeps its selector and type encoding. The runtime snapshot
([phase0.md §9](phase0.md)) must be identical before and after the port
while the class stays in Objective-C. For a class that changes language it
must be identical in meaning: methods with their type encodings, protocols,
superclass and decoded property attributes match exactly, the systematic
differences the Swift compiler introduces are classified and listed for the
reviewer, and what the runtime cannot verify (weak versus unowned) is
checked against the source. The comparison tool does not classify those
differences yet and gives no verdict for such a class; a Phase 0 item builds
that. If the runtime sees the same class, hidden callers keep working
whether or not anyone found them. This is the defense that does not rely on
search being complete. It covers only the build configuration that the test
scheme builds, because that is the only one the tool can snapshot.

**Find the callers** with the census ([phase0.md §2](phase0.md)) whenever the surface is
going to change: an `undynamic` commit, a rename, removing `@objc`, deleting a
method, changing a parameter type. The rest of this section is about making
that search trustworthy.

Rule that follows from both: **a port commit never deletes a method because it
appears to have no callers.** Apparent dead code is ported, and removing it is
a separate later commit with an empty census.

**Deleting apparent dead code** (the owner, 2026-11-22; decisions.md). Each
method is judged by itself; a sample's error rate decides nothing.

- When in doubt, keep it.
- An empty census is necessary and not sufficient. For a class that
  descends from `NSView` or any other framework class, implementing a
  method can be all it takes to change what the framework does: AppKit
  asks `respondsToSelector:` and behaves differently for a class that
  answers yes. So the selector must also be one the frameworks do not know
  about. The census already keeps a method out of "no caller found" when a
  framework header declares the selector or a framework class implements it
  ([phase0.md §2](phase0.md)). It does not yet see a selector that a
  framework only refers to (an informal protocol or a private delegate
  method that no class implements and no header declares): until a check
  of the selector references in the frameworks' binaries exists, no method
  of a class with a framework ancestor is deleted.
- Read the history of the method (`git log -S` on its selector, and the
  commits that added it and removed its last caller). Why it was added and
  how it became orphaned is evidence: a caller removed on purpose supports
  deletion; a method added to satisfy the system, a nib, a script or a
  plugin does not.
- The deletion's commit message records the evidence for each method.

## 2. The reflective-site registry

Any place that turns a string into a selector or class, turns a selector into
a string, or asks the runtime for methods can reach methods that are named
nowhere near it. There are few enough of these to list every one. The
registry is a table in `docs/swift-migration/reflective-sites.md` with one row
per site: file and function, what it does, and **the set of selectors or
classes it can reach**, expressed as an explicit list or as a pattern.

The census consults the registry, so a query for any selector reports the
reflective sites that can reach it. Building the registry is a Phase 0 task:
every hit for the searches below is read and classified, and nothing is left
as "probably fine".

A lint keeps the registry complete: a new use of any API in section 3
outside the registered sites fails the gate until it is added.

Sites that only log or compare (`DLog(@"%@", NSStringFromSelector(_cmd))`) are
registered as harmless, so that it is recorded that someone looked.

Examples already found, which show the kinds of thing to expect:

| Site | What it does | Reach |
|---|---|---|
| `iTermAdvancedSettingsModel.m`, `+enumerateMethods:` | Walks the class's method list with `class_copyMethodList` and calls methods by name prefix. The methods themselves are generated by macros that paste tokens into names | Every class method whose name starts with `advancedSettingsModelDictionary_` or `load_`; and `deprecated_` plus a setting name, built by string concatenation and tested with `respondsToSelector:` |
| `PTYTextView.m`, `validateMenuItem:` | Enables a menu item when its action's name has the prefix `contextMenuAction` | Every method whose selector starts with that prefix. Renaming one disables its menu item; adding one enables it |
| `TmuxStateParser.m` | `[value performSelector:NSSelectorFromString(converter)]`, where the converter name comes from a table of strings | The `NSString` category methods named in that table |
| `TmuxGateway.m`, `TmuxController.m` | Store a callback selector as a string in a dictionary and convert it back later | Every selector passed as a tmux command callback |
| `PseudoTerminal.m`, tab group menu | Builds menu items from an array of title and selector-name strings | The selectors named in that array |
| `iTermTextViewContextMenuHelper.m`, `iTermURLActionFactory.m` | Dictionaries mapping action identifiers to selector names, converted with `NSSelectorFromString` | The selectors in those dictionaries |
| `iTermAdvancedSettingsViewController.m` | Builds getter and setter selectors from setting names | Class methods of `iTermAdvancedSettingsModel` |
| `iTermReflection.m` | Reads a method's argument count and types from the runtime and splits the selector on `:` | Any method registered as a scripting function; depends on type encodings |
| `iTermFloatingPaneView.swift`, `MenuItemPopupView.swift`, `iTermApplication.m` | Private AppKit selectors by name | AppKit, not our code |

The first row is the hard case and it sets the standard. A search for any one
advanced setting's selector finds nothing useful, because the name is
assembled by the preprocessor and looked up by prefix. A port of that file
that wrote the settings as ordinary Swift properties would compile, pass a
caller search, and silently stop loading every advanced setting. The runtime
snapshot catches it, because hundreds of class methods would be missing.

Macros themselves are not rows of the registry. By the owner's decision of
2026-11-20 ([decisions.md](decisions.md)), the reading of each macro that
hides a caller, a method definition or control flow lives in
`docs/swift-migration/macro-classification.tsv`, one row per macro, checked
by `codedb.py macrolint` (section 6); the registry points to it. Anything
unexpected or surprising about a macro that porting will need is also
written as a comment in the code at the macro's definition. A name a macro
builds that a registered site looks up, like the prefixes above, stays in
the registry.

## 3. What to search for

Selector and string conversion:

- `NSStringFromSelector` (about 60 in `sources/`, 64 in the whole app by the
  owner's count). Each one is read. The questions: is the string stored,
  compared, used as a dictionary key, used as a key path, concatenated, or
  tested with `hasPrefix:` or `hasSuffix:`? Is it later converted back?
- `NSSelectorFromString`, `sel_registerName`, `sel_getUid`, `sel_getName`,
  Swift `Selector("...")` and `NSSelectorFromString`.
- String concatenation, `stringWithFormat:`, and `##` in macros whose result
  becomes a selector or part of a method name.
- `_cmd` used for anything other than logging: as a dictionary key, as an
  associated-object key, or passed along as a callback.

Calling by selector:

- `performSelector:` and every variant, `makeObjectsPerformSelector:`,
  `sortedArrayUsingSelector:` and `sortUsingSelector:` (the selector is sent
  to every element, so each element class must implement it),
  `NSInvocation`, `methodForSelector:`, `instanceMethodForSelector:`,
  `objc_msgSend` and its variants, `NSTimer` and `NSNotificationCenter`
  selector registration, `NSUndoManager` target and selector registration,
  `NSApp sendAction:to:from:`, `tryToPerform:with:`, `targetForAction:`,
  `supplementalTargetForAction:sender:`, `NSAppleEventManager`
  `setEventHandler:andSelector:`.

Asking whether something responds:

- `respondsToSelector:`, `instancesRespondToSelector:`,
  `conformsToProtocol:`, `isKindOfClass:` with a class obtained from a string.
  These change behavior silently when a method disappears: the code takes the
  other branch.

Forwarding and proxies:

- `forwardInvocation:`, `forwardingTargetForSelector:`,
  `methodSignatureForSelector:`, `resolveInstanceMethod:`,
  `doesNotRecognizeSelector:`, and `NSProxy` subclasses (`iTermWeakProxy`,
  `iTermWeakReference`). A call made through a proxy is written against the
  proxy and lands on the target.

The runtime API:

- Method lists and lookups: `class_copyMethodList`, `class_getInstanceMethod`,
  `class_getClassMethod`, `method_getName`, `method_getImplementation`,
  `method_getTypeEncoding`, `class_copyPropertyList`, `property_getName`,
  `protocol_copyMethodDescriptionList`.
- Method replacement: `method_exchangeImplementations`,
  `method_setImplementation`, `class_addMethod`, `class_replaceMethod`,
  `imp_implementationWithBlock`.
- Class manipulation: `objc_allocateClassPair`, `objc_registerClassPair`,
  `object_setClass`, `objc_getClass`, `objc_lookUpClass`, `NSClassFromString`,
  `NSStringFromClass` where the string is stored or compared,
  `NSProtocolFromString`.
- Associated objects.

  Fourteen files use the method and class manipulation calls today, among them
  `iTermSelectorSwizzler.m`, `NSObject+iTerm.m`, `NSTableView+iTerm.m`,
  `iTermColorMap.m`, `VT100ScreenStateSanitizingAdapter.m`,
  `iTermScriptingWindow.m`, `iTermWeakProxy.m` and `iTermWeakReference.m`.

Methods found by naming convention, which Cocoa looks up by assembling a name:

- Key-value coding accessors and the scripting accessors built on them
  (`insertObject:in<Key>AtIndex:`, `removeObjectFrom<Key>AtIndex:`,
  `valueIn<Key>WithUniqueID:`, `objectSpecifier`).
- Key-value observing helpers (`keyPathsForValuesAffecting<Key>`,
  `automaticallyNotifiesObserversFor<Key>`).
- Validation (`validate<Key>:error:`), `application:delegateHandlesKey:`.
- Key paths in `NSPredicate` format strings, `NSSortDescriptor` keys, and
  bindings.
- `NSCoding` and state restoration methods.

A method a Swift class exposes for any of these is `@objc`, and `@objc dynamic`
where it is swizzled, observed, or reached through key-value coding.

## 4. xib files

The app has 70 xib files with heavy ties to Objective-C code. Each of the
following is a reference to code that only resolves when the nib loads or when
the user acts.

**Custom classes (235 distinct).** A xib names a class as a string. If the
class is not found at load time, AppKit logs "Unknown class" and instantiates
the base class instead. Nothing crashes; the view just does not behave. A
Swift class is found under its bare name only if it is declared
`@objc(Name)`. Otherwise the xib must name the Swift module, as 23 attributes
already do. Rule: the port pins the name with `@objc(Name)` and **the xib file
is not edited in a port commit**. A port commit that touches a xib is doing
two things at once.

**Outlets (about 1,800 connections).** An outlet is set with key-value coding
when the nib loads. A missing or misspelled property raises "not key value
coding-compliant" at load.

- Each outlet stays `@IBOutlet` and `@objc` with the identical name.
- **Ownership is preserved.** Xcode's Swift template writes
  `@IBOutlet weak var`. Many Objective-C outlets are strong. Changing a strong
  outlet to weak releases any object that nothing else retains: a top-level
  object in the nib, or a view that the code removes from its superview and
  adds back later. A strong outlet stays strong.
- An outlet is nil until the nib loads and nil forever if the connection was
  removed in the xib. Objective-C code tolerates that through nil messaging.
  Declare outlets as optionals and use optional chaining; the lint forbids the
  implicitly unwrapped form that Xcode's template uses.
- Code that runs before the nib loads (an initializer touching an outlet) did
  nothing in Objective-C and must do nothing in Swift.

**Delegate and data source outlets (206 and 31).** An object wired up as a
delegate in a xib is asked `respondsToSelector:` for each optional method.
Objective-C lets a class implement those methods without declaring that it
conforms to the protocol, and it still works. In Swift, a method that is not
tied to a declared protocol conformance is exposed under whatever selector
Swift derives, or not at all, and the delegate call silently stops arriving.
Rule: a ported class declares conformance to every protocol whose methods it
implements. The compiler then warns about near misses, and the runtime
snapshot confirms the selectors.

**Actions with a specific target or File's Owner (750 connections, 259 of
them to File's Owner).** The xib stores a selector string. The method must be
`@IBAction` with the same selector. For File's Owner the class in the xib is
only a hint; the real owner is whatever object the code passes when it loads
the nib, so the census resolves the owner from the loading code as well as
from the xib. Nib names are strings in code (about 115 places) and are not
changed by a port.

**First Responder actions (226 connections, 192 distinct selectors, all in
`MainMenu.xib`, which has 294 actions in total).** These are the hardest case
and need the most care:

- The action has no target. When the menu item is chosen, or when the menu is
  about to be shown and needs validating, AppKit walks the responder chain
  (the focused view and its superviews, the window, its delegate, the window
  controller, the application, the application delegate) and uses the first
  object that responds to the selector.
- So the caller of `-[PTYTextView biggerFont:]`, or of the same selector on
  any other class that implements it, is a line of XML in `MainMenu.xib`, and
  which class receives it depends on what has focus.
- **Failure is silent.** If a ported method loses `@objc`, changes selector, or
  changes its parameter list, nothing responds and the menu item is simply
  greyed out. If two classes implement the selector and one stops responding,
  the action goes to the other one, which is worse.
- The implementers of a First Responder selector are every class that
  implements that selector, anywhere, plus AppKit for standard actions such as
  `copy:`. The dossier lists, for each First Responder action the unit
  implements, all the other implementers and where they sit in the chain.
- The binding test ([phase0.md §3](phase0.md)) records the set of app classes implementing
  each First Responder selector and fails if a port changes the set.
- Menu validation refers to the same selectors: `validateMenuItem:`,
  `validateUserInterfaceItem:` and `validateToolbarItem:` (about 72 uses)
  compare `item.action` with selectors, and at least one compares by name
  prefix. In Swift, `#selector` comparisons are checked by the compiler;
  comparisons by string are registered as reflective sites.
- The same selectors are reached from other places that do not go through the
  xib: key bindings that invoke a menu item by selector, the code that finds a
  menu item by its action, the API's menu item invocation, the touch bar, and
  toolbar items. These are found by the census.

**Bindings (4) and user-defined runtime attributes (21).** Both go through
key-value coding with a key stored in the xib (`hasSelection`,
`blackAndWhite`, `helpText`, `alphaAllowed`, and others). The property must be
`@objc`, and `@objc dynamic` for a binding so that observation fires.

**Nib loading and initializers.**

- Views in a xib are created with `initWithCoder:`, not `initWithFrame:`. A
  Swift subclass must provide `init?(coder:)`, and it must do what the
  Objective-C one did, including nothing at all if the Objective-C class
  inherited it. A Swift class with stored properties that lack defaults does
  not inherit initializers, which is a common way to break nib loading.
- `awakeFromNib` (about 134 implementations) runs after outlets are connected.
  It can run more than once for an owner that loads several nibs. Preserve it
  exactly.
- Top-level objects in a nib are owned by whoever loaded it. A port that
  changes how the owner holds them changes their lifetime.
- Tags and identifiers set in the xib are looked up from code (about 94
  places). They are data, not selectors, and are unaffected by a port, but a
  ported class must not change the code that assumes them.

**Menu items and controls built in code** (about 545 places assign an action)
behave like xib actions but are visible to the compiler when written with
`@selector` or `#selector`. The ones written as strings are reflective sites.

**What the dossier contains for a unit with xib ties:** every xib that names
its classes; for each, the outlets with their ownership, the actions with
their targets, the bindings and runtime attributes; and for each First
Responder action it implements, the other implementers. The census produces
this by parsing the xib XML and resolving each connection's target id to an
object and its class.

**What checks it:** the runtime snapshot, the binding tests, the best-effort
nib-loading test, and a runtime check chosen by the rule in [lifecycle.md §1](lifecycle.md)
("Verifying runtime behavior"). Automated tests do not exercise the responder
chain with real focus, so units with First Responder actions, or with many
outlets and actions, get hands-on QA on a test VM. For a unit with a few
outlets and no First Responder actions, a nib-loading test, or a temporary
change that opens the affected window and exercises its actions, may be
enough.

## 5. Handling by mechanism

| Mechanism | Count | Handling |
|---|---|---|
| `performSelector` family | 80 | `undynamic` prep commit to a direct call or a block where the target and selector are static. Where the selector is data, keep it, keep the target method `@objc` with the identical selector, and register the site |
| `NSSelectorFromString`, `NSStringFromSelector` on non-literals | about 14 and about 25 | Registered, with reach. Selectors in reach are pinned and carry a comment at the method naming the site |
| `respondsToSelector` | 162 | Usually optional protocol methods. Keep the protocol in Objective-C until all conformers and callers are Swift, and keep the selector spelling exact |
| `NSClassFromString` | 16 | Pin class names with `@objc(Name)` |
| Method-list enumeration | 2 files | Registered. The enumerated class is ported only with a design for how its methods remain discoverable, reviewed by the owner |
| Swizzling and method replacement | 14 files use the runtime API | The swizzled class stays in Objective-C until the swizzle is removed, or the method is `@objc dynamic` and covered by a test that the swizzle still takes effect |
| Proxies and forwarding | 6 `forwardInvocation:` | The proxy stays in Objective-C. Targets keep `@objc` selectors and type encodings |
| xib classes, outlets, actions | section 4 | Section 4 |
| AppleScript | 141 | Binding tests. Scripting classes keep names, keys, and key-value coding compliance (`@objc dynamic`) |
| Key-value coding and observing | few | `@objc dynamic`; keep key spelling |
| Associated objects | 5 | Not to be added. Existing ones are ported only with the owner's permission, per `CLAUDE.md` |

When a method later loses `@objc` in stage two, that is its own commit, the
census for its selector must be empty, and the registry must show no site
that can reach it.

## 6. Macros

The preprocessor can define methods, call methods, and build names, and none
of it is visible to a search of the source text. Macros hide both sides: the
definition of a method that is called normally, and the call of a method that
is defined normally.

A script classified the multi-line macros in `sources/` and
`ThirdParty/PSMTabBarControl`:

| What the macro does | Macros | Where |
|---|---|---|
| Sends a message | 33 in 10 files | `DebugLogging.h` (17), `iTermAdvancedSettingsModel.m`, `iTermPreferences.m`, `PSMYosemiteTabStyle.h`, `PSMRolloverButton.m` |
| Stringifies an argument | 15 in 3 files | `DebugLogging.h`, `iTermAdvancedSettingsModel.m`, `iTermTests.h` |
| Contains `return`, `break`, `continue` or `goto` | 13 in 6 files | `iTermAdvancedSettingsModel.m`, `iTermPreferences.m`, `ScreenChar.h`, `iTermWeakReference.h`, `DebugLogging.h` |
| Uses `_cmd`, `__FILE__`, `__LINE__`, `__func__` | 11 in 4 files | `DebugLogging.h`, `PSMYosemiteTabStyle.h`, `PSMRolloverButton.m`, `iTermCLogging.h` |
| Defines a method | 9 in 3 files | `iTermAdvancedSettingsModel.m` (5), `iTermPreferences.m` (3), `iTermWeakReference.h` (1) |
| Pastes tokens into a name | 8 in 3 files | `iTermAdvancedSettingsModel.m` (5), `DebugLogging.h`, `CVector.h` |
| Defines a class | 1 | `iTermTests.m` |
| Applies a method-family attribute | 1 | `iTermCopyModeHandler.h` |

The numbers are small enough that every one of these macros is read, and
its reading (what it expands to and reaches) is written in
`macro-classification.tsv`, to which the reflective-site registry (section
2) points. The script that made this table was not committed. By the decision of
2026-11-19 the classification starts from the macro definitions and
expansions the compiler records ([decisions.md](decisions.md)).
`codedb.py macros` lists each macro with its kinds as facts decide them; a
macro also has the kinds of the macros it expands, to any depth, marked
with the macro they come through ("send (via DLog)"), and a macro from
outside the repository counts as one that sends when the database records
a send from its body. `codedb.py macrolint` is a lint over the file
`docs/swift-migration/macro-classification.tsv`, which has one row per
macro of these kinds that the migration's scope defines or expands, with a
column for a reading (what the macro expands to and reaches) written by
the person who read it. `macrolint --write` adds the rows, marked
UNREVIEWED; the lint fails on a macro with no row, a changed definition and,
unless `--allow-unreviewed` is given, on an UNREVIEWED row. By the owner's
decision of 2026-11-20 ([decisions.md](decisions.md)) the readings live in
this file, not in the reflective-site registry, which points to it, and
anything unexpected or surprising about a macro that porting will need is
also written as a comment in the code at the macro's definition. Whether
UNREVIEWED rows fail the gate is still open for the owner. The table above counted multi-line macros only. The lint covers
the macros of these kinds that a captured unit reads, in the captured
configuration. It does not see macros in code that no unit compiles
(`STOPWATCH_START` and `STOPWATCH_LAP` in `DebugLogging.h`, the
`iTermTests.h` and `iTermTests.m` macros in the table above) or in other
build configurations; it lists the `#define`s it finds in such code, as
text, without failing on them.

**`iTermAdvancedSettingsModel.m` is the reference case.** Its `DEFINE_*`
macros are used 532 times, and reading them in full turned up every one of the
following. Each is a general pattern to look for elsewhere.

1. **Methods defined by token pasting.** One use of `DEFINE_BOOL(fooBar, ...)`
   defines class methods named `advancedSettingsModelDictionary_fooBar`,
   `fooBarUserDefaultsKey`, `load_fooBar`, and `fooBar`. The settable variants
   add `setFooBar:`. The secure variants add `object_fooBar` and
   `setFromObject_FooBar:`. The deprecated variant adds `deprecated_fooBar`.
   None of these names appears in the source.
2. **Methods found by enumeration, not by name.** As described in section 2, the
   class walks its own method list and calls whatever starts with
   `advancedSettingsModelDictionary_` or `load_`.
3. **Selector strings built with a format.** The secure variant stores
   `[NSString stringWithFormat:@"setFromObject_%s:", #capitalizedName]` and
   `@"object_%s"` in a dictionary. A view controller later turns those strings
   into selectors. The string and the method it names are produced by the same
   macro from the same argument, and neither is written out anywhere.
4. **Calls into a Swift class by pasted name.** The secure variant calls
   `iTermSecureUserDefaults.instance.defaultValue_##name`,
   `[[iTermSecureUserDefaults instance] name]`, and
   `[[iTermSecureUserDefaults instance] set##capitalizedName:newValue]`. So an
   existing Swift class has members whose only Objective-C callers are macro
   expansions. Searching the source for one of those member names finds the
   Swift definition and no callers. This is the case most likely to lead
   someone to delete a method as unused or to drop its `@objc`.
5. **A stringified name that becomes stored state.** `@#name`, capitalized, is
   the user defaults key for the setting. The method name and the persisted
   key are the same token. Renaming the method silently renames the key, and
   every user's saved value for that setting is lost. Macro stringification
   must be checked against [stored-state.md](stored-state.md) as well as against callers.
6. **Hidden static storage.** Each use declares
   `static iTermAdvancedSettingSlot sAdvancedSetting_fooBar`. A port needs an
   equivalent with the same lifetime and the same thread-safety.
7. **Functions passed as tokens.** The `transformation` and
   `inverseTransformation` arguments are names of functions, pasted in as
   calls. Those functions have no callers that a search can find, and one is
   already wrapped in a pragma to silence an unused-function warning.
8. **Conditional definition.** Some macros exist only under
   `#if ITERM2_SHARED_ARC`, and defaults depend on `#if BETA`. What a macro
   expands to depends on the target and configuration being built, so an
   analysis of one configuration is not an analysis of all of them.
9. **Arguments evaluated more than once, or not at all.** A macro argument is
   pasted wherever it appears, so an expression with a side effect can run
   twice, or zero times. `DLog` does not evaluate its arguments when logging
   is off. A Swift function evaluates each argument exactly once unless the
   parameter is an autoclosure. Every function-like macro that a ported method
   uses is checked for this.

Other macros that define methods: the `FAST_BOOL_ACCESSOR` family in
`iTermPreferences.m` (11 uses, each defining a class method with a hidden
static cache) and `ITERM_WEAKLY_REFERENCEABLE` (3 files, which define a
`weakSelf` method on 6 classes).

Two further kinds matter for porting even though they do not hide callers:

- **Control flow inside a macro.** A macro that contains `return` or `break`
  makes a function leave from a line that does not look like an exit. This
  affects the extraction rules in [large-code.md §2.2](large-code.md) and every port: expand the
  macro mentally, or with the preprocessor, before translating.
- **Attributes that change ownership or method family**, such as the
  `objc_method_family(none)` macro in `iTermCopyModeHandler.h`, and
  `NS_RETURNS_RETAINED`, `NS_CONSUMED` and the `CF_RETURNS` family. Under ARC
  a selector beginning with `copy`, `new`, `init`, `alloc` or `mutableCopy`
  transfers ownership to the caller unless an attribute says otherwise. A
  ported method with any of these attributes, or with a name in one of those
  families, needs individual attention and a lifetime test.

**How macros are covered:**

- **The runtime snapshot** ([phase0.md §9](phase0.md)) sees every method a macro defines,
  because it reads the compiled class. A toy test confirmed a method defined
  by token pasting appears in the method list. This covers the definition
  side completely, for the configuration that was built.
- **The code database covers the call side** ([phase0.md §10](phase0.md)).
  The Clang AST attributes a send made inside a macro to the place the macro
  is used and contains methods whose names are built by token pasting, so
  the database's queries see them. This replaced the earlier plan to search
  preprocessed source as text ([decisions.md](decisions.md), 2026-11-19).
- **Selector references in object files** are the third check: a compiled
  object file records every selector its code references, after all
  expansion. By the same decision, the database is checked against the
  app's object files, every selector an object file sends explained by the
  database and the reverse, and the number of call sites of each selector
  against the database's send sites. `codedb.py crosscheck` is that
  cross-check ([phase0.md §10](phase0.md)).
- **Every configuration that defines different macros** (ARC and non-ARC
  targets, beta and release) is searched separately. The runtime snapshot
  can only be taken of the configuration that the test scheme builds
  ([phase0.md §9](phase0.md)), so a method that a macro defines only in
  another configuration is not seen by it.
- **Stringified names are checked against stored state.** Any macro argument
  that is both a method name and, through `#`, a string is traced to see
  whether the string is persisted.

**Porting code that is built from macros.** Swift has no preprocessor. The
choices are a generator script that writes the Swift from a table, Swift
macros, or a table of data in place of generated methods. While Objective-C
